# Phase 05 — QA Review Round

Instructions for the Sr. QA Analyst agent. This file is loaded once per review round.

The QA agent's job is to verify that the PR meets its acceptance criteria and is genuinely production-ready — not to find as many issues as possible, but to ensure no real problem ships.

---

## Before reviewing

1. Read `roles/sr-qa.md` — internalize the persona before starting
2. Read the PR's acceptance criteria from the active plan
3. Read prior round reports (if round > 1): `pr-logs/[branch]/round-[N-1]/qa-report.json`
4. Read `memory/qa-learnings.md` — know what patterns have caused issues before in this project
5. Read `memory/patterns.md` — know the established patterns so you can validate against them

---

## Review dimensions

Work through all dimensions. Do not skip any because the PR "looks simple."

### 1. Acceptance criteria
Verify each criterion from the active plan independently. Mark each as `pass`, `fail`, or `partial`. A `partial` is a `fail` for merge purposes.

### 2. Code quality
- TypeScript: no `any`, no type assertions without justification, no suppressed errors
- No DRY violations: look for copy-pasted logic that should be a shared utility
- SOLID: each function/class has one clear responsibility
- No dead code (unreachable branches, unused exports, commented-out blocks)
- No TODO comments without a linked open-decisions item

### 3. Tests
- Tests exist for all new functionality
- Tests cover the happy path AND error/edge cases
- Tests are not just checking implementation details (no testing internals)
- Test descriptions are readable: "should return 401 when token is expired" not "test auth"
- No skipped or `.only` tests committed

### 4. Error handling
- All async operations have explicit error handling
- No silent `catch (() => {})` blocks
- API routes return appropriate HTTP status codes with structured error bodies
- User-facing errors show helpful messages, not stack traces

### 5. Security (every PR, not just auth PRs)
- No secrets, tokens, or credentials in code or committed files
- No `console.log` of sensitive data
- SQL queries use parameterised inputs — no string interpolation
- File paths sanitised before use
- Dependencies: no known critical CVEs in newly added packages (`pnpm audit`)

### 6. Performance
- No N+1 queries
- No blocking synchronous operations on hot paths
- Images (if any) have explicit dimensions to prevent layout shift
- No memory leaks (event listeners have cleanup, subscriptions are unsubscribed)

### 7. Accessibility (frontend PRs only)
- Interactive elements are keyboard-accessible
- Images have meaningful alt text
- Form inputs have associated labels
- Colour contrast passes WCAG AA
- Run `@axe-core/playwright` and include results in report

### 8. Visual validation (frontend PRs with approved mockups)
Run Playwright screenshot comparison:
```typescript
// Generated by playwright-templates.md
await page.goto('http://localhost:3000/[route]')
await expect(page).toHaveScreenshot('[component]-expected.png', { threshold: 0.1 })
```

If no prior screenshot exists, capture one as the baseline. Flag significant deviations from the approved mockup HTML as `major` issues with screenshot attached.

### 9. Edge cases — always check these
- Empty state (no data, new user, empty list)
- Maximum input (very long strings, large file uploads, high counts)
- Concurrent requests (two users doing the same action simultaneously)
- Auth expiry during an operation
- Network failure mid-request
- Invalid/malformed input at every API boundary

## Bug report format

Write to `pr-logs/[branch]/round-[N]/qa-report.json`:

```json
{
  "pr": "pr-003",
  "branch": "wpr/feature/auth",
  "round": 1,
  "reviewer": "sr-qa",
  "reviewed_at": "ISO-timestamp",
  "acceptance_criteria": [
    { "criterion": "JWT expires after 15 minutes", "status": "pass" },
    { "criterion": "Refresh token rotates on use", "status": "fail", "note": "rotation not implemented" }
  ],
  "bugs": [
    {
      "id": "bug-001",
      "severity": "blocker",
      "dimension": "security",
      "location": "src/lib/auth.ts:47",
      "title": "JWT secret read from process.env without fallback — throws in test environment",
      "repro": "Run pnpm test — all auth tests fail with 'Cannot read property of undefined'",
      "expected": "JWT_SECRET has a test fallback or tests mock the env var",
      "actual": "Unhandled TypeError crashes the test suite",
      "suggested_fix": "Add: const secret = process.env.JWT_SECRET ?? (process.env.NODE_ENV === 'test' ? 'test-secret' : (() => { throw new Error('JWT_SECRET required') })()"
    }
  ],
  "verdict": "fail",
  "merge_blocked_by": ["bug-001", "bug-002"],
  "minor_deferred": ["bug-005"],
  "playwright_results": {
    "tests_run": 8,
    "passed": 7,
    "failed": 1,
    "failed_tests": ["auth flow > should redirect after login"]
  }
}
```

Severity classification:
- `blocker` — prevents merge. Security issue, test failure, acceptance criterion fails, data loss risk.
- `major` — must fix this round. Wrong behaviour, missing error handling, accessibility failure, significant visual deviation.
- `minor` — should fix but can defer. Code style, non-critical UX improvement, minor performance issue. Goes to `known-issues.md`.

### How to write a good bug report

Each bug must be:
- **Reproducible** — someone else can follow `repro` and observe the `actual` result
- **Specific** — include file path and line number where known
- **Actionable** — `suggested_fix` is not mandatory but speeds up the fix round significantly
- **Independent** — one bug per entry, even if two bugs have the same root cause

Do not write vague bugs like "improve error handling" — name the specific function, the specific error condition, the specific expected behaviour.

---

## Verdict

`verdict` is one of:
- `pass` — no blockers, no majors. Ready for merge gate.
- `fail` — one or more blockers or majors. Dev fix round required.
- `escalate` — round 3 with unresolved blockers. Stop, notify user.

If `verdict: pass`, update `session.yaml → round_state: merge-gate` and proceed to `phases/06-merge-gate.md`.

If `verdict: fail` and `round < 3`, update `session.yaml → round_state: fix-in-progress` and trigger the fix round in `phases/04-execution.md` Step 5.

If `verdict: fail` and `round == 3`, update `session.yaml → round_state: escalated` and notify the user:

```
⚠  PR-[N] has unresolved issues after 3 review rounds.

Outstanding blockers:
  [bug-id] [title]
  [bug-id] [title]

Options:
  1. I'll review the issues and instruct you on how to proceed
  2. Skip this PR and flag it in known-issues.md (not recommended)
  3. Abort and revisit the approach

What would you like to do?
```
